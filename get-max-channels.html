Approach 1

New AudioContext({ sinkId }) Per Device

Non-Blocking Close

Instantiates a brand-new hardware AudioContext initialized with { sinkId } for each device, reads destination.maxChannelCount synchronously, and immediately disposes the context with void audioContext.close(). 

// Executed for each output device sinkId:
const audioContext = new AudioContext({ sinkId });
const maxChannels = audioContext.destination.maxChannelCount;
void audioContext.close();

Approach 2

Single Suspended AudioContext + setSinkId() Reuse

1 Context + Non-Blocking Close

Creates a single AudioContext, suspends it immediately, then loops through all devices calling await audioContext.setSinkId(sinkId) and reading maxChannelCount before disposing the shared context with non-blocking void audioContext.close(). 

const audioContext = new AudioContext();
// Do NOT await suspend() before loop (stalls in autoplay-blocked state)
void audioContext.suspend();
for (const sinkId of sinkIds) {
  await audioContext.setSinkId(sinkId);
  results.push(audioContext.destination.maxChannelCount);
}
void audioContext.close();

Under the Hood: Why They Differ

  • • Approach 1 (Synchronous Constructor + Fire-and-forget Close): new AudioContext({ sinkId }) synchronously queries the audio backend descriptor for maxChannelCount during construction and kicks off void audioContext.close() asynchronously. However, spinning up many simultaneous AudioContext instances in a tight loop can hit browser hardware context limits (often 6–64 concurrent contexts before garbage collection/teardown finishes).
  • • Approach 2 (Suspended Reuse via await setSinkId): Allocates only one AudioContext and immediately calls suspend() so the audio rendering thread doesn't pump silence. Each await audioContext.setSinkId(sinkId) awaits an asynchronous IPC handshake with the browser's audio service to rebind the output device descriptor and update destination.maxChannelCount.
  • • Why Approach 2 Can Throw Err (And How It's Solved):
    1. Virtual Pseudo-Device IDs (NotFoundError): enumerateDevices() returns pseudo-IDs like "default" and "communications". While new AudioContext({ sinkId }) sometimes tolerates or ignores them during sync construction, await audioContext.setSinkId('communications') strictly validates against physical/OS sink IDs and rejects with NotFoundError unless normalized to "".
    2. Iframe Permission Policy / Ununlocked Devices (NotAllowedError): Calling setSinkId(nonDefaultId) requires either active microphone permission (getUserMedia) or the speaker-selection Permissions-Policy header.
    3. Calling setSinkId While suspend() Is Pending (InvalidStateError): Using void audioContext.suspend() or awaiting properly prevents overlapping state transitions.
